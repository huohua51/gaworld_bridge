# GAWorld 与 YuLan-OneSim：T4 注册传递横向试验

## 结论先行

这轮横向试验已经完成，但只能回答一个窄而重要的问题：在题目、提示词、
GLM-5.2、推理参数和评分逻辑完全相同的条件下，把消息传递机制换成
YuLan-OneSim 的 `EventBus` 后，T4“注册消息是否能沿完整链路送达、被目标接受并
触发正确动作”的模式是否保持。

在 17 个完整结束的匹配格中，YuLan-OneSim 与 GAWorld 的 FullPass 逐格一致，
一致率为 **17/17**。YuLan 的 6 个 full 格全部形成了接收者回执验证的完整路径，
目标送达、目标接受和正确动作均为 **6/6**。因此，在本轮已经观察到的 T4 范围内，
没有发现两套平台的功能差异。

第 18 格不是能力失败，而是运行进程被外部终止。它已经发出调用并留下部分证据，
所以按预注册规则没有补跑，而是在最严格的固定分母口径中计为失败。于是总分表现为：

| 口径 | GAWorld | YuLan-OneSim | 应如何解释 |
| --- | ---: | ---: | --- |
| 完整匹配格逐格一致 | 17/17 | 17/17 | 已完成格未观察到平台差异 |
| 18 格固定分母 FullPass | 12/18（66.7%） | 11/18（61.1%） | 1 格差来自外部进程中断 |
| full 链路 | 6/6 | 6/6 | 两边都能完成注册消息闭环 |

这不是“YuLan 总体等于 GAWorld”的证明，也不是两个项目的总排名。样本只有三张
任务表面、一个模型和一个 seed；统计上不足以证明等效，更没有覆盖 H1–H7 人类效度。

## 为什么不能直接运行 YuLan 自带场景然后比数字

两个项目的原生任务、角色、终止条件和指标定义不同。直接把各自 README 中的成功率
并排，会同时改变平台、题目、模型和评分器，任何差异都无法归因。这里采用的是
“协议同面”设计：复用 GAWorld 的三张 T4-v2 任务及角色提示，只把消息传递部分换成
YuLan 的真实 `EventBus`。这使比较对象收窄为平台传递机制。

它也带来一个必须公开的边界：Agent 角色是评测适配器，不是 YuLan 某个原生社会场景
自动生成的角色。因此结果说明“YuLan EventBus 能承载该协议”，不说明 YuLan 的全部
原生场景已经通过 GAWorld Benchmark。

## 如何保证两边做的是同一道题

试验前冻结了以下条件：

- 三张任务：水质、变电站负荷、学校空气质量；
- 两个条件：control 与 intervention；
- 三条轨道：full、remove_bridge、drop_bridge；
- 模型：Paratera 上的 GLM-5.2；
- `temperature=0`、关闭 thinking、每次最多 256 tokens；
- 原 T4-v2 提示生成函数和评分逻辑；
- 18 格、最多 60 次调用、无事后替换。

规则模型预跑了完整 18 格，预期模式全部通过。随后将 GAWorld 参考与 YuLan 规则预跑
的 60 个提示哈希按多重集比较，完全相等。真实运行中，17 个完整格共有 57 对
request/response；它们与 GAWorld 相应 17 格的提示哈希也完全相等，57 个响应全部满足
JSON 契约，且没有最终记账的 provider error。

## R0 为什么先发现了一个测量陷阱

付费运行之前，R0 用确定性 Agent 检查了 YuLan 原生事件证据。完整链、断桥负对照和
未知目标未实际接收都符合预期，多跳父子关系在本测试中也能保持。但原生 flow 导出有
两个缺口：

1. 未知目标的单事件流在导出时被省略；日志里虽有 warning，却没有结构化失败格；
2. 发往 `all` 的全局 `EndEvent` 在跟踪前就被消费，导出中看不到终止证据。

这意味着不能把 EventBus 内部的“处理尝试”直接当作“实际送达”。本试验因此增加了
接收者侧 `add_event` 回执，只有接收者记录同一 `event_id` 才算 delivered；终止也由
适配器另行登记。这个修补发生在预注册和真实运行之前，没有修改 YuLan 源码。

## 分轨结果

| 轨道 / 条件 | GAWorld | YuLan 固定分母 | 机制含义 |
| --- | ---: | ---: | --- |
| full / control | 3/3 | 3/3 | 正常状态沿完整路径送达并保持当前动作 |
| full / intervention | 3/3 | 3/3 | 行动要求沿完整路径送达并触发变更 |
| remove / control | 3/3 | 3/3 | 无更新时 keep_current 仍正确 |
| remove / intervention | 0/3 | 0/3 | 切断桥后无法获得变更所需证据 |
| drop / control | 3/3 | 2/3 | YuLan 少的一格是外部中断 |
| drop / intervention | 0/3 | 0/3 | 丢包后不能凭空执行干预动作 |

这里 remove/drop 的 intervention 失败是负对照的预期结果，不代表模型坏了。它证明
干预动作依赖消息桥，而不是目标 Agent 在没有证据时猜中答案。

## 中断如何处理

原运行完成 8 格后，在 `substation_load / control / drop_bridge` 中断。损坏尾部包含 NUL，
但接收回执证明 source 已经把消息送到第一中继，中继阶段开始后未留下完整响应证据。
处理方式是：

- 原目录保持不动并冻结关键文件哈希；
- 不重打中断格；
- 新建续跑注册，只执行后面从未开始的 9 格；
- 合并时把中断格记为 0，同时单独标注原因为基础设施流失。

这样做牺牲了一个分数，却避免“只补跑失败/缺失格”造成选择性偏差。也正因为有这个
中断，本轮只能称为完成的先导横评，不能进入正式排行榜。

## 能说与不能说

可以说：YuLan-OneSim 的单机 EventBus 在补充接收回执后，能够承载 GAWorld T4-v2
注册传递协议；17 个完整匹配格与 GAWorld 完全一致，full 路径 6/6 成功。

不能说：YuLan 与 GAWorld 全面等效；YuLan 原生 50 多个场景都通过了本指标；
YuLan 的 H1–H7 人类效度更好；或者 61.1% 与 66.7% 是平台能力差。最后一个差值已被
证据定位为外部执行中断。

## 下一步

下一轮应优先做 T5 eligibility-scope 同面适配，因为它能检验消息到达之后，约束范围
是否真的影响目标决策；这比重复扩大 T4 数量带来的信息更多。之后再选 YuLan 原生
`two_step_flow_model` 做“原生场景覆盖审计”，把任务构造能力与 EventBus 承载能力分开。
若要形成平台排名，则需要新的密封任务表面、至少多个 seed，并预先规定等效界限和
基础设施流失处理规则。
