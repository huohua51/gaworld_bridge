# T3 非代码独立审核：GAWorld / YuLan-OneSim 同面实验报告

## 1. 这轮实验回答什么

本轮不是比较两个项目 README 中已有的分数，而是在同一套新任务上比较一条具体因果链：提案者提交候选方案，独立审核者读取只有自己可见的核验材料，给出批准或拒绝，执行者只根据已经送达的审核决定更新状态。

三个任务分别是社区诊所高温降温点、图书馆延时开放和食物银行扩大配送，不含代码；每个任务都有“证据支持提案”和“证据与硬约束冲突”两种条件。GAWorld 使用真实 `ReviewChannel`，YuLan-OneSim 使用锁定提交 `9829d722` 的真实 `EventBus`。任务语义、提示词、GLM-5.2 设置、角色契约和评分器完全共用。

矩阵是 3 个任务 × 2 个证据条件 × 2 个平台 = 12 格。每格依次调用 proposer、reviewer、executor，总计 36 次逻辑调用。temperature=0、thinking=disabled、每次最多 256 tokens，不对失败格做人工重试或替换。本轮注册文件在第一次真实调用前已提交于 `62ad57a`，注册文件 SHA-256 为 `2ac3ab56ac51e7d15ea809b72222816c173878660b2875b557f3764ab4f11446`。

## 2. 付费前校准

确定性 Oracle Fixture 的 12/12 格全部通过，36/36 个结构化响应有效；GAWorld 与 YuLan 的 6/6 个配对中，三个角色的提示词哈希、角色输出和最终状态全部精确一致。它证明任务、Oracle、评分器和两个适配器在输入相同时能够产生相同结果，也验证了私有证据没有进入 proposer 或 executor 的提示词。

因此，后面的真实失败不能简单归因于离线适配器写错；必须继续区分模型输出、解析边界和平台事件传递。

## 3. 冻结主结果

| 指标 | GAWorld | YuLan-OneSim | 合计/说明 |
|---|---:|---:|---|
| 可测量单元 | 6/6 | 6/6 | 12/12 |
| FullPass | 0/6 | 1/6 | 1/12 |
| 严格 JSON 契约响应 | 12/18 | 10/18 | 22/36 |
| proposer 严格有效 | 6/6 | 4/6 | 10/12 |
| reviewer 严格有效 | 0/6 | 1/6 | 1/12 |
| executor 严格有效 | 6/6 | 5/6 | 11/12 |
| 私有证据隔离 | 6/6 | 6/6 | 12/12 |
| 角色读写边界 | 6/6 | 6/6 | 12/12 |
| 平台轨迹与模型轨迹完整 | 6/6 | 6/6 | 12/12 |

主分数不能改成“语义其实对了”。冻结协议要求响应本身是单个 JSON 对象，任何代码围栏都属于接口契约失败；失败响应保留在固定分母内。GAWorld 的 0/6 与 YuLan 的 1/6 是这次运行的真实、不可回填主结果。

但它也不能被解释为“YuLan 比 GAWorld 强”。模型调用发生在外部，同一模型对相同提示有时返回裸 JSON、有时返回 Markdown 围栏 JSON。两个平台各自独立调用模型，平台并不生成或清理这些原始文本。

## 4. 首错到底在哪里

36 个响应中有 14 个被严格解析器拒绝：GAWorld reviewer 6 个；YuLan proposer 2 个、reviewer 5 个、executor 1 个。14/14 的原始文本都被完整的 Markdown JSON 代码围栏包裹，没有空响应，也不是字段缺失；`RecordedModelRunner` 对整个原始字符串直接执行 `json.loads(raw.strip())`，所以在第一个反引号处报 `Expecting value`。

为了判断模型是“不会做题”还是“会做但包装错”，进行了不改变主分数的事后诊断：只剥除一层完整 JSON 代码围栏，再运行相同字段验证器。结果如下：

- 14/14 个失败响应都能恢复为合法 JSON 对象并通过角色字段契约；
- 12/12 个 proposer 的候选方案与注册方案精确一致；
- 12/12 个 reviewer 的 approve/reject、证据 ID、失败条件和 reason code 均与 Oracle 一致；
- reviewer 全对象精确一致为 10/12，另外两个 `proposal_id` 为空，因为它们收到的是被上游严格解析器清空后的提案；
- 12/12 个 executor 都正确遵循了它在本次实际链路中看到的“有审核/无审核”状态；
- 只有 6/12 个最终状态命中任务 Oracle：六个冲突条件即使没有审核也会保留基线，因此“最终状态正确”可能只是碰巧正确，不能替代完整因果链证据。

所以本轮主要发现不是 GLM-5.2 不会判断硬约束，而是结构化输出边界不稳：模型的核心判断基本正确，Markdown 包装使审核消息无法进入平台通道，进而让执行者按“审核缺失”安全地保留基线。

## 5. 为什么横向排名无效

平台配对的提示词一致性必须按阶段看：proposer 为 6/6，reviewer 为 4/6，executor 为 3/6。两个 YuLan proposer 因代码围栏被解析为空对象，后续 reviewer 提示自然与 GAWorld 分叉；最后一个 YuLan reviewer 成功返回裸 JSON，executor 提示也随之与 GAWorld 分叉。全链三个角色哈希同时一致的配对只有 3/6。

这不是“实验偷偷给了平台不同题”，而是动态链路中上游输出成为下游输入的必然后果。不过，它意味着当前一轮独立抽样无法隔离平台效应。最有力的例子是食物银行冲突条件：reviewer 提示在两边完全相同，GAWorld 那次外部调用返回围栏 JSON，YuLan 那次返回裸 JSON；前者断链，后者成为唯一 FullPass。差异发生在模型文本格式，不发生在 ReviewChannel/EventBus。

平台侧能下的结论很有限：离线确定性输入下两边均为 6/6；真实运行中，唯一一条严格有效的审核被 YuLan 正确送达并由 executor 读取；所有单元的私有信息隔离、角色写权限、轨迹和最终提交证据都完整。GAWorld 没有得到一条严格有效的 live reviewer 输出，因此这轮没有足够机会估计它在真实审核有效时的交付率。

## 6. 发现了哪些实现问题，建议怎样改

### 6.1 结构化输出只靠提示词约束，接口没有真正约束 JSON

GAWorld 的 `OpenAIProvider` 当前只发送 model、messages、max_tokens、temperature、thinking 等字段，没有暴露 `response_format` 或 JSON Schema；Bridge 的 `RecordedModelRunner` 又只接受可直接 `json.loads` 的裸对象。实验以 14/36 个围栏响应和 11/12 个 reviewer 围栏响应发现了这条接口缝隙。

建议由后续实现同学按两层修复：

1. 如果当前 Paratera/GLM 兼容端确认支持，优先让 `OpenAIProvider` 接收并传递 provider-native `response_format` / JSON Schema，而不是只在用户提示中写“只返回 JSON”。
2. 在公共结构化响应层增加保守规范化器：仅接受“整个响应恰好是一层 Markdown JSON 围栏且内部是唯一 JSON 对象”的情况；必须保留原始文本、规范化规则、规范化后哈希和验证错误。不要用贪婪正则从任意说明文字中抠 JSON。
3. 把“传输格式有效”和“任务语义正确”分开报告。宽松恢复只能作为诊断，不能静默改写已经冻结的严格主分数。
4. 增加回归测试：裸 JSON、完整围栏 JSON、围栏外多余文字、多个 JSON 对象、截断 JSON和错误字段枚举都要分别覆盖。

### 6.2 自动重试没有进入实验调用证据

运行控制台观察到两次 TLS EOF，GAWorld `_retrying` 自动发起传输层重连。模型证据仍只记录 36 个逻辑调用，因此输出目录不能独立重建真实 HTTP 尝试数。两个失败尝试很可能没有生成可计费完成文本，但这仍影响成本审计、延迟分析和“禁止重试”的解释。

建议给 provider 调用返回或旁路记录 `logical_call_id / http_attempt / retry_reason / started_at / ended_at / billed_usage`；评测模式允许设置 `attempts=1`，或者同时冻结逻辑调用上限与物理请求上限。本报告只记录“控制台观察到 2 次自动重连”，不把它伪装成输出包内可独立验证的指标。

### 6.3 独立模型抽样不能单独识别平台效应

当前设计让两个平台各自重新调用模型，上游非确定性会改变下游提示。下一轮应把问题拆成两个实验：

- 平台因果隔离实验：平台中立地生成或预先登记一套提案、审核和执行 payload，然后将完全相同的 payload 重放进两个通道；比较送达、拒绝、重复、过期、越权和状态变更。模型只生成一次，平台是唯一变化量。
- 端到端系统实验：若要把“平台调度 + 模型调用”作为整体比较，则随机/交叉平衡平台顺序，增加独立重复和任务表面，报告变异与置信区间；不能用一对独立调用做排名。

### 6.4 原生语义边界必须保留

GAWorld `ReviewChannel` 原生只有 `approve/revise`，本实验把共同协议的 `reject` 放进 `revise` 载体，并在 executor 提示前恢复成 `reject`。因此不能声称 GAWorld 原生提供了 reject 枚举。YuLan 的 EventBus 负责事件路由，现实任务、审核规则和状态转移仍是 Benchmark 适配层定义，也不能声称这些是 YuLan 的原生业务能力。

## 7. 这轮工作实际取得了什么

第一，T3 从单一代码阈值任务扩展到了三个非代码社会协作表面，并明确验证了“私有证据—独立审核—状态更新”的因果链。第二，离线 12/12 对齐证明同面适配方法可工作。第三，真实实验没有为了得到漂亮数字而放宽解析或补跑，反而定位出一个高频、可复现、可交接修复的结构化输出缺口。第四，严格 FullPass 阻止了“冲突条件碰巧保留基线”被误算为成功。第五，本轮说明公平横向比较不能只写“相同模型、temperature=0”，还必须控制每一阶段实际进入模型的提示和上游输出。

## 8. 当前结论和下一步

当前证据支持：两个平台都能在确定性 payload 下承载这条 T3 链；GLM-5.2 对三类硬约束的核心判断为 12/12 正确；现有结构化响应接口会因 Markdown 围栏高频断链。当前证据不支持：YuLan 优于 GAWorld、两个平台总体等效、T3 已全面完成，或任何 H1–H7 真人效度结论。

下一步不应补跑本轮。先把本报告交给负责 GAWorld/Bridge 接口的同学，按新版本实现并回归结构化输出与重试证据；同时新建“单次采样、双平台重放”的平台隔离协议。修复在开发任务上通过后，再用全新的非代码密封任务和新预注册做端到端复测。
